# Internationalization (i18n) — 9 languages

The app UI is available in 9 languages. Users pick one in
**Settings → Language**, or leave it on **Follow device settings**
(the default), in which case the device language is used if it is
supported, and English otherwise.

| Tag | Language | Notes |
|---|---|---|
| `ja` | 日本語 | Source language — every string is written here first |
| `en` | English | Fallback when the device language is unsupported |
| `zh` | 简体中文 | Simplified Chinese; all Chinese device locales map here |
| `es` | Español | |

| `ko` | 한국어 | |

Language names in the picker are shown in each language's own
script (the platform convention) and are not themselves translated.

## How it is implemented

- All user-visible strings live in
  `app/src/main/java/app/quantusnode/node/StringsTable.java` — a
  pure-Java table (no Android dependencies) with one map per
  language.
- `I18n.java` resolves the effective language (explicit pick →
  device language → English) and formats values.
- The app intentionally does not use `res/values-*`: the UI is built
  programmatically and the manual build pipeline links no resources.
  The code table also lets us verify completeness mechanically on a
  JVM — every key must exist in every language, and format
  placeholders must match the Japanese source. That check currently
  reports **153 keys × 9 languages, 0 missing**.

## Decisions worth knowing

- **Numbers are ASCII digits everywhere.** Block heights, peer
  counts and durations always render with digits 0-9 in all 9
  languages (formatting pins `Locale.US`). Arabic and Hindi do not
  switch to local digit shapes. Since versionCode 26, the values
  the UI shows use 3-digit grouping (e.g. `357,605`); the
  diagnostic records and the notification keep the ungrouped form.
  Quantity (plural) strings are stored per category as
  `<key>.zero/.one/.two/.few/.many/.other` and selected in code
  from the actual count, which stays a long.
- **Terms are kept consistent per language** — e.g. block / peer /
  syncing / uptime terms do not vary between the dashboard and
  the notification within one language.
- **Arabic (RTL):** the layout direction follows the language, so
  rows and alignment mirror instead of breaking. This is a
  "readable, not broken" level of RTL support, not a full RTL
  design pass — the pulse visual is symmetric and unaffected.
- The foreground-service notification follows the selected language
  the next time it is rebuilt. Notes recorded by the service keep
  the language they were written in.

## Improving a translation

Native-speaker review is very welcome — the current translations
have not yet had one. To fix a string:

1. Edit the language's map in `StringsTable.java`.
2. Update the corresponding cell in the table below.
3. Keep the format placeholders (`%1$d`, `%2$d`, `%1$s`) exactly as
   they are in the Japanese source — the app fills them in.
4. Open a pull request. Changing one cell is a perfectly good PR.

To add a language: add its tag to `StringsTable.TAGS`, a full map
(153 keys), its own-script name to `StringsTable.LANGUAGE_NAMES`,
and the language-code mapping in `I18n.java`.
